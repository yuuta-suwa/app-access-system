# 権限管理手順（管理者マニュアル）

## 0. 基本ルール

- **閲覧許可（8 分類）と管理者ロールは別物**です。「全分類 ON」にしても管理者にはなりません。
- 画面で隠すのではなく、DB（RLS）が許可範囲外のデータを返しません。管理画面の操作もすべて DB 側で管理者か再確認されます。
- 権限変更は理由の入力が必須で、操作者・対象者・内容・日時・理由が監査ログに残ります（編集・削除不可）。
- 管理画面から他人の SELF を閲覧・検索・編集する機能はありません。
- 自分自身のアカウント状態とロールは変更できません（別の管理者に依頼）。有効な管理者が 0 名になる変更は拒否されます。

## 1. 最初の管理者を登録する（初回のみ・DB 運営者）

1. 管理者になる人が公開 URL から Google でログイン → 「承認待ち」画面になることを確認。
2. Supabase ダッシュボード → SQL Editor で `supabase/scripts/bootstrap_first_admin.sql` を開き、
   `REPLACE_WITH_ADMIN_EMAIL@example.com` を実際のメールに置換して実行。
3. 本人が「状態を再確認」を押すと、ヘッダーに「管理」が表示される。
4. **2 人目の管理者**を管理画面から登録する（喪失時の復旧のため 2 名以上を推奨）。

Google ユーザーが自分で管理者権限を設定する経路はありません（権限テーブルへの書込権限が無く、`user_metadata` も判定に使いません）。

## 2. 新しい利用者を承認する

**方法 A：本人がログイン → 管理者が承認**

1. 本人が Google でログイン（pending になる）。
2. 管理 → 利用者管理 → 一覧（承認待ちが先頭）から本人の「編集」。
3. アカウント状態を「利用可能（active）」に。
4. 8 分類の ON/OFF を設定（「8 分類すべて許可」「すべて解除」「プリセット」も利用可。適用後に個別修正可）。
5. 変更理由を入力 → 「保存」→ 確認ダイアログで差分を確認 → 「保存する」。
   「保存」を押すまで DB は更新されません。「変更を取り消す」で編集前に戻せます。

**方法 B：事前招待**

1. 利用者管理の下部「事前招待」にメール・分類・理由を入力して登録。
2. 本人が初回 Google ログインした時点で、Google が検証したメールが一致すれば active＋指定分類で自動的に紐づけ。
   管理者ロールは付与されません。メール未検証のアカウントは pending のまま。

## 3. 権限を変更・撤回する

- 利用者詳細で分類を OFF → 理由 → 保存。対象者の**次回データ取得から**その分類の分類名・目的・アプリ名・URL は返りません
  （ログイン中の画面も、画面復帰時・5 分ごとの再確認で自動的に作り直されます）。
- SELF に保存済みだった共通アプリは「アクセスできない項目」と表示され、本人は削除のみ可能です。

## 4. 利用停止・再開

- 状態を「利用停止（suspended）」にして保存。停止中は分類・SELF を含むすべてのデータ取得が拒否されます（SELF の内容は保持）。
- 再開は「利用可能」に戻すだけです。分類設定は保持されています。
- （任意）Google アカウント側のセッションも即時に切りたい場合は、Supabase ダッシュボード → Authentication → Users で該当ユーザーを Ban / セッション削除。

## 5. ロール（creator / admin）

- 利用者詳細の「ロール」欄で設定。理由必須。active 利用者のみ。
- creator：共通アプリの登録申請ができる（閲覧できる分類は別途の分類許可に従う）。
- admin：利用者承認・分類権限・共通アプリ掲載を管理。付与時は確認ダイアログが出ます。

## 6. 権限プリセット

- 管理 → 権限プリセットで作成・編集・削除。初期値：「全分類」「LIFE STAGE1.0」「不動産事業チーム（不動産事業＋資料作成チーム）」「指定なし（SELFのみ）」。
- 「不動産事業チーム」の関連分類は仮設定です。運用に合わせて修正してください。
- **プリセットを編集しても既存利用者の権限は変わりません**。必要なら各利用者を個別に保存し直してください（監査ログに残ります）。

## 7. 共通アプリ・目的・登録申請

- 管理 → 共通アプリ・目的：分類ごとの「やりたいこと」を登録し、アプリを目的に紐づけます。
  複数分類に載せる場合も**同じアプリを再利用**し、各分類の目的に紐づけます（正本は 1 件）。
- 公開状態：下書き（非公開）／公開／停止／廃止。「公開」かつ許可分類の目的に紐づく場合だけ利用者に見えます。
- 利用 URL は「利用者が開く URL」を登録します（管理用 URL は登録しない）。https のみ。
- 機密性が異なるアプリは、掲載する分類を意図的に限定してください。
- 管理 → 登録申請：creator の申請を確認し「承認して公開」または「差戻し」。承認前に URL と管理責任者を確認してください。

## 8. 定期運用

- **月 1 回の権限棚卸し**：利用者一覧で状態・許可分類数・最終ログインを確認し、不要な許可・長期未ログインを見直す。変更履歴で想定外の操作が無いか確認。
- 管理者は常に 2 名以上。退職・異動時は先に後任を admin にしてから、前任のロールを外す。
- 管理者を全員失った場合：DB 運営者が `bootstrap_first_admin.sql` で復旧（監査ログに `bootstrap: DB operator` として記録）。
- 監査ログの保持期間・エクスポート方法は運用で決定（未決事項）。

## 9. 注意

- DB の運営権限（Supabase の Secret key・DB パスワード）を持つ人は技術的にすべてのデータにアクセスできます。
  「運営者でも絶対に閲覧不可能」とは説明しないでください。
- 外部アプリの URL を知っている人がそのアプリに直接アクセスすること自体は、このポータルでは防げません。移動先アプリのアクセス制御はそのアプリの管理者の責務です。
